# 03 — SQLite Database Specification

**Version:** 1.0.0  
**Database:** SQLite  
**Schema version:** 2

## 1. Principles

- One `project.sqlite` per project directory.
- Foreign keys enabled.
- WAL mode preferred.
- Core query fields are relational columns.
- Flexible metrics/evidence metadata may use JSON text.
- UTC timestamps stored as ISO-8601 strings.
- Media timeline positions stored in seconds as REAL.
- IDs are UUID strings generated by application.

## 2. Required PRAGMAs

On connection:

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
```

## 4. Enum validation

Application-layer validation SHALL restrict:

### `analysis_runs.status`
- `QUEUED`
- `INSPECTING`
- `ANALYZING`
- `GENERATING_EVIDENCE`
- `GENERATING_REPORT`
- `COMPLETED`
- `CANCELLED`
- `FAILED`

### `analysis_runs.overall_result`
- `PASS`
- `WARN`
- `FAIL`
- NULL before completion

### `findings.severity`
- `INFO`
- `WARN`
- `FAIL`

### `findings.disposition`
- `OPEN`
- `CONFIRMED`
- `FALSE_POSITIVE`
- `IGNORED`

### `detector_executions.status`
- `PENDING`
- `RUNNING`
- `COMPLETED`
- `FAILED`
- `CANCELLED`
- `SKIPPED`

## 5. JSON serialization rules

All JSON text SHALL:

- be UTF-8;
- use JSON object/array syntax, never Python repr;
- avoid NaN/Infinity;
- use stable field names from specs;
- include units in field names where ambiguous.

Example:

```json
{
  "true_peak_dbtp": -0.2,
  "threshold_dbtp": -1.0
}
```

## 6. Migration strategy

- `schema_meta['schema_version']` begins at `1`.
- Every schema change requires a numbered migration.
- Never alter a user project without backup/recovery strategy.
- Migration runs inside transaction where SQLite permits.
- Failed migration leaves original DB usable or restored.

## 7. Profile snapshot requirement

`analysis_runs.qc_profile_snapshot_json` stores the full exact profile document used by the run.

Later edits to `qc_profiles` MUST NOT change historical run interpretation.

## 8. Deleting media/project data

V1 MAY allow deleting a project from inside the app only if explicitly implemented.

Deleting a project MUST NOT delete source media.

Deleting findings manually is not required; disposition is preferred for auditability.

## 9. Database acceptance criteria

- Foreign-key violations fail.
- Reopening project preserves runs/findings/evidence references.
- Historical run profile snapshot remains unchanged after profile editing.
- Deleting a media asset from DB cascades run records only after explicit user action.
- Source file is untouched by DB cleanup.

## 10. Phase 8 migration 002 — advisory AI reviews

Version 1 projects migrate transactionally to version 2 after canonical schema
validation. A SQLite backup, including committed WAL data, is retained as
`project.schema-v1.sqlite.bak` before migration. Failure rolls back the migration.
Existing deterministic records are unchanged.

```sql
CREATE TABLE ai_reviews (
    id TEXT PRIMARY KEY,
    finding_id TEXT NOT NULL REFERENCES findings(id) ON DELETE CASCADE,
    model_id TEXT,
    model_version TEXT,
    prompt_version TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('COMPLETED', 'UNAVAILABLE')),
    error_code TEXT,
    output_json TEXT,
    created_at TEXT NOT NULL,
    UNIQUE(finding_id)
);

CREATE INDEX idx_ai_reviews_finding ON ai_reviews(finding_id);
```

Each reviewed finding has one separate review record. Unavailable reviews have
a null output and an explicit error code; model identity may be null when absent.
Output JSON uses the AI specification schema; prompt version and UTC creation
time are stored separately. Unreviewed findings beyond the bounded review budget
have no row and the UI explicitly labels their review unavailable.
